# 5. Failure Mode and Effects Analysis (FMEA)

Date: 2026-11-12. Source baseline: `a4aac3a`. Scope: options execution, lifecycle integrity and financial/audit evidence.

## Method and limits

All 22 requested scenarios appear in two linked matrices. Matrix A records preconditions, trigger, expected behavior, potential failure and present controls. Matrix B records detection, containment, recovery, verification and residual risk. Read rows with the same ID together.

**Expected behavior is a proposed engineering acceptance target, not a claim of current implementation.** Automatic liquidation, retries with uncertain outcomes, adoption of manual exposure, signal TTL, session rules and risk thresholds require the open policy decisions in the [requirements audit](FUNCTIONAL_REQUIREMENTS_AUDIT.md). No such values or permissions are invented here.

Current-state evidence is from the reviewed source and [technical review](TECHNICAL_DESIGN_CODE_REVIEW.md), not new production experiments. **S** = source-supported failure path; **P** = offline reproduction in earlier audit steps; **T** = existing deterministic tests cover part of the scenario. Neither S nor P establishes historical production occurrence. Proposed fault-injection tests below have not been executed as part of this FMEA.

Severity/priority:

- **P0 / Critical:** could create unintended/duplicate transactions, leave unmanaged exposure, or lose the evidence needed to reconcile actual orders. Resolve before treating restart/failure recovery as unattended-safe.
- **P1 / High:** could miss/wrongly apply decisions, choose wrong instruments, or corrupt accounting/audit interpretation.
- **P2 / Medium:** recoverable service degradation without current evidence of direct exposure corruption.

Priorities are qualitative engineering judgments based on consequence and current controls. No occurrence frequencies, numerical detection probabilities or RPN scores are assigned: production incident frequencies and monitoring effectiveness have not been measured. Residual risks describe what remains **after proposed controls**, not an assertion that those controls exist.

## Priority groups and common-cause failures

### First: prevent unintended transactions and irreconcilable exposure

FM01, FM09–FM16, FM20 and FM22 share a common requirement: durable identity, order intent, idempotent fill accounting, exclusive executor ownership and startup/account reconciliation. Existing in-process cumulative-fill and cancellation checks should be retained, not replaced with automatic retries.

**Highest-priority next task remains startup reconciliation plus single-account execution ownership**, with durable-intent work alongside it. A flat-account check alone is insufficient when a submit outcome is unknown or another executor is running.

### Second: keep protection meaningful during degraded service

FM02, FM03, FM06, FM08, FM10 and FM18 expose the distinction between stopping new orders and protecting existing exposure. The current implementation often stops the process for either. Introduce separate admission/protection health and approved outage action, including validating any broker-held protective-order capability. A locally evaluated 2% breach rule cannot bound loss during absent data, network outage, gaps or unavailable liquidity.

### Third: establish instrument and record correctness

FM07, FM17, FM19, FM21 and FM22 require complete metadata, strict normalized schemas, clock discipline and an execution ledger. P&L reporting is not presently implemented; do not use funds balance changes, target prices or estimated premium as substitutes for attributed realized results.

### Compound scenarios requiring dedicated tests

| Combination | Why individual tests are insufficient | Required oracle |
| --- | --- | --- |
| Submit accepted -> response timeout -> disk failure -> restart | No local ACK/record may survive despite actual exposure | No retry-as-new; UNKNOWN until broker attribution resolves; zero duplicate entry |
| Partial target exit -> cancel timeout -> late fill -> emergency breach | Duplicate replacement could create short exposure | Reconcile final cumulative fills before replacement; total attributed sells never exceed buys |
| Feed loss -> token expiry -> exit rejection | No fresh price and no usable broker operation | Protection-degraded/entry-disabled state, explicit escalation; never report flat or protected without evidence |
| Telegram backlog -> old EXIT reply -> newly active trade | Correctly parsed command can affect wrong position | Reply maps to original signal; zero mutation of new active trade |
| Manual broker square-off -> delayed local poll -> local stop fires | Local quantity no longer matches account | Reconciliation/ownership policy prevents an unintended sell beyond allocated exposure |
| Duplicate worker -> shared SQLite -> same signal | Database uniqueness alone does not fence broker submissions | One execution owner and one intent dispatch; losing worker cannot submit |
| Crash after fill -> missing execution prices -> financial export | Quantity recovery alone cannot establish realized P&L | Report incomplete financial record until prices/charges/attribution reconcile |

These are proposed fault-injection scenarios, not claims they occurred in production.

## Verification protocol

1. Preserve existing tests and execute new tests against mocks/fake transports, a temporary database, injected clocks and a fake broker state store that survives simulated process restart.
2. Cover before-dispatch, accepted-but-no-response, partial/full execution, cancel-race and crash-before-persist boundaries separately.
3. Assert invariants: acknowledgement never creates exposure; duplicate cumulative fill does not increase exposure; attributed sells do not exceed buys; unknown outcome is not retried as new; cancelled signal does not revive; unresolved recovery blocks admission.
4. Assert record integrity: immutable source/intent/order identities, explicit timestamps, complete or explicitly incomplete execution/financial evidence, no secret-bearing output.
5. Record which tests pass, what remains policy-blocked and which live capabilities remain unverified. Run the full suite after implementation changes; green mocks do not certify external service timing or liquidity.
6. Use controlled non-ordering shadow/replay validation before any separately authorized live rollout. Do not interrupt the current production engine to execute this FMEA.

## Open policy/evidence dependencies

- Maximum acceptable quote age, order visibility delay, cancel wait and retry budget are not specified; acceptance tests must parameterize approved limits rather than invent them.
- Automatic liquidation, manual-position adoption, shared-account behavior, session/expiry rules and concurrent signal capacity need owner decisions.
- P&L scope, cost basis, fees/taxes, marking source, reporting currency and broker-statement reconciliation tolerance need an accounting specification; none is inferred.
- No fresh production logs, broker statements, incident frequency data, network fault measurements or full SDK transport audit were obtained in this step.
- Current detection largely relies on console output and snapshots, not independently verified alert delivery. Proposed detectors must be implemented and exercised before claiming risk reduction.
